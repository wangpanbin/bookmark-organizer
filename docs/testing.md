# 闸门体系

三类闸门，**缺一不可**。判据统一是**用户可见的承诺**或**磁盘上真实发生的事**，
不是内部变量 —— 仓库前科：面板报 100% 成功、书签栏一点没变。

| 命令 | 是什么 | 成本 | 能改源码 |
|---|---|---|---|
| `npm test` | 正向：单测 | 2 秒，零浏览器 | 否 |
| `npm run test:falsify` | **证伪**：造坏实现，确认闸门会红 | 分钟级 | ⚠️ **是** |
| `npm run test:e2e` | E2E：真实浏览器 + 真实用户路径 | 分钟级，开有头浏览器 | 否 |
| `python tools/verify_all.py` | 上面全部 + 面板契约 + 压缩包真加载 | 分钟级 | ⚠️ **是**（含证伪） |

## 1. 正向闸门（`tests/unit/`，23 个文件）

覆盖 URL 归一化、去重、规则匹配、计划生成、类目合并、storage 契约、去重逐条否决、
失败日志降级路径、模型接入四层、链接健康的纯函数层与编排层、语义去重、归档客户端，
以及**死代码可达性**。

条数会变，**别在文档里写死**——写死的数字会变成没人更新的谎话。
要当前条数看 `python tools/precommit.py` 的输出。

`tests/fixtures/samples.js` 是命中率闸门的输入（阈值 70%）。

### 值得单说的三个文件

**`tests/unit/reachability.test.js`** —— 查「声明为已完成的导出是否真被引用」、
「消息处理器是否真注册进了 `HANDLERS`」、「面板引用的 DOM id 是否真在 html 里」。
它存在是因为 2026-10-06 的评审抓到一个反复出现的失败模式：
**模块写了、单测也绿了，但没有任何地方调用它** —— 而这看起来非常像「功能完成」。
给一个没人调的函数写 10 条单测，证明不了任何东西。

> ⚠️ **这道闸门查的是「名字在别的文件里出现过」，不是「被调用过」。**
> 一行 `import { foo } from './x.js'` 就足以满足它 —— 2026-10-06 实测：
> 删掉调用点只留 import，18 条相关单测一条没红。
> 关键逻辑要**额外**断言调用，判据找 `foo(`，**括号是关键**。

**`tests/unit/scope-list.test.js`** —— 手动指定范围的清单纯逻辑。
最要紧的一条是 `reconcileList` **不按 URL 认领**：夹具里那条失效书签有一条
**同 URL** 的替身，而替身是用户没勾的。认回来就等于整理了范围外的东西，
正是这个功能要防的那类事故。同一份文件里还有一组「该放行的必须放行」的自检 ——
只钉拦住不钉放行的话，一个永远返回空数组的实现能全绿。

**`tests/unit/scope-guard.test.js`** —— 执行侧范围校验。
`isInScope` 的语义里 `null` 与 `[]` 是两件不同的事，最容易写错的是把
`!allowed.length` 当成「没限制」，那会让「清单空着」变成「整棵树随便动」。
另外三条是**位置断言**：校验必须排在 `chrome.bookmarks.move` 之前、
`scopeIds` 必须落进 task（service worker 空闲 30 秒即被回收，续跑是**新进程**
从 storage 读回这个 task 的）、执行器不许自己去读清单。

> ⚠️ 这道闸门只测纯函数那一层，**抓不到恒真实现** —— 把 `isInScope`
> 整个换成 `return true`，纯函数测试仍然通过。真正兜住它的是
> `tests/e2e/scope-run.js` 的两组对照，以及 `product_falsification.py`
> 里那条「范围校验形同虚设」的证伪用例。

**`tests/unit/root-id-literal.test.js`** —— 根 id 字面量的回归闸门。
守的是同一条根因的**第二次**犯法：2026-10-05 那次 45 条书签全军覆没的根因
是「根 id 是常量」，第一次在 `targetRoot` 设置项上（由 `target-root.test.js` 守着），
第二次在 `src/backup.js` —— 它自己定义了 `ROOT_ID = { BAR:'1', ... }`，
注释还写着「根 id 是固定契约」。**第一道闸门对此全绿**，因为它量的是一个
没有覆盖到出问题那条路径的指标。

判据刻意很窄：只抓 `ROOT_ID` 标识符、`parentId: '1'|'2'|'3'`、
以及 `|| ['2']` 这种路径退化。**不得**误报 `roots.js` 里那段刻意的旧设置
迁移映射（读用户存的 `'1'` 翻译成语义键，那是**读**，不是**写死 id 给 API 用**）——
判据文件里有一条专门钉这个的用例。

**`tests/unit/scan-logic.test.js` 里的「具名导入必须真的被导出」** ——
`tree.js` 从来没有导出过 `getFlatTree`，而 `scheduler.js` 与 `background.js`
都在引它。解构出 `undefined` → `await undefined()` 抛 TypeError → 被 catch 吞掉
并 `return []`，于是 link-scan 与语义去重**从来没跑起来过**，且全程零报错。

只钉「不许再出现 `getFlatTree` 这个名字」是不够的：下次换个名字写错同一件事，
闸门照样绿。所以判据一般化成「从 `tree.js` 的具名导入必须真的在它的导出里」。

**`tests/unit/storage.test.js`** —— 给 `chrome.storage.local` 装最小替身。
storage.js 是全项目最容易**静默**损坏数据的模块，之前只能靠 E2E 间接覆盖，定位成本极高。
有了替身就能在 Node 下直接测两条契约：① 读-改-写全程持锁（并发 50 次不丢更新）
② `mutateMany` 的回调收到的是映射。

**`tests/unit/veto.test.js`** —— 同样用替身测「逐条否决」：执行器跳过被否决条目、
否决名单按 id 而非 URL、并发切换不丢更新。它是**双向**钉死的 ——
既钉「该跳过的跳过了」，也钉「没误跳过该删的」。
删掉执行器里那行 `if (isDedupeVetoed(...)) continue`，这 3 条立刻变红。

**`tests/unit/inject-path.test.js`** —— 守「`tools/inject_key.py` 写的路径必须是
`llm.js` 真能读到的路径」这条**契约**。刻意不测「key 文件在不在」——
那个文件是 gitignore 的、换台电脑就没有，拿它当判据会变成随机红。
`python tests/falsify_inject_path.py` 会打坏补丁证明这 3 条确实会红。

## 2. 证伪闸门（`tests/unit/falsification.test.js` + `tests/product_falsification.py`）

每个用例的结构都是：**故意造一个坏实现 → 断言对应闸门【确实报错】→ 说明闸门有效**。

`npm run test:falsify` 会**备份真实源码**、打上坏补丁、跑整套测试、断言变红、再还原。
当前覆盖的退化：剥掉全部 hash、剥掉全部 query、给 `plan.js` 注入写操作 import、
注入**跨行**写操作 import、注入**动态** import 写操作模块、字典位置参数错位、
给 `plan.js` 注入**日志模块**、发送成功后整条清空缓冲、`recordFailure` 不再兜底、
把「归入位置」又写死成根 id、**把失败当成成功读**、**去掉 30s 超时**、
**capturingFetch 不透传 init**、**注入的 key 被写进 storage**、**百炼漏掉 regionBound**。

> 后 5 处是接入 pi-ai 时新增的，对应「换底层最容易悄悄坏掉」的五件事：
> 失败不 reject、超时被摘掉、signal 断链、密钥落盘、区域诊断丢失。
>
> 有一条是闸门自己抓出来的：最初 `llm.js` 里留了一份 `REQUEST_TIMEOUT_MS = 30_000`
> 的副本（只为方便看），结果 runtime.js 把真值改成 0 时那道断言照样绿 ——
> **同一个值在两处各存一份，等于给退化留了一条绕路**。已删副本，闸门才变红。

### ⚠️ 跑之前必读

> **`npm run test:falsify` 不是只读的。** 它会**修改真实源文件**、跑一遍整套、再还原。
> 所以它**不能和任何编辑或测试并发** —— 已经因此拿到过一次假失败
> （证伪正在给 `normalize.js` 注入 `indexedDB`，而同时跑了 `npm test`，
> 纯链路闸门理所当然地红了）。
>
> 跑它的时候：**什么都不做，等它自己结束。** 单次运行是分钟级。
>
> 另外它结束时**必须 rc=0**：退化全红但有一处关键字没匹配上时脚本同样返回 1 ——
> 那不是「闸门失灵」，是**量具没对准**，看输出里的「实际标题」那一行去改关键字。

### 放宽判据要双向证伪

收紧容易，**放宽**才是真正危险的那一半 —— 删掉一条断言就能让自己「变绿」，
而删断言永远不会被任何东西拦。

| 方向 | 判据 | 2026-10-06 的实例 |
|---|---|---|
| **该绿** | 一次**正当**的改动不得变红 | 措辞改得更强（「不改你的书签」→「一个字都不改」）、超时常量 30s→45s |
| **该红** | 一次**坏**改动必须变红 | 措辞改成含糊的「会谨慎处理书签」、超时被说成「请求失败」 |

只有「该红」那一侧是容易糊弄过去的 —— 它通常会红，因为坏改动确实更坏。
**「该绿」那一侧才是判据的真正考验**：一条写死字面量的判据会在正当改动上红，
而那种红是**误报**，误报的闸门比没有闸门更糟（大家只会学会忽略它，真违规也一起被忽略）。

记不住时问一句：**这条判据防的失效变了吗，还是只是措辞变了？**

### ⚠️ 没有东西会自动调用它们

> 绿灯本身不算证据。一道从来没红过的闸门，和没有闸门是一样的。
>
> 2026-10-06 之前，`ui_contract_gate.py` 与 `contrast_gate.py` **两个文件都存在、
> 都能跑、都全绿，但没接在任何地方** —— 与本文档反复记着的那个失败模式原样吻合。
> 170 条单测与 10 处证伪点从来没被要求跑过，于是「全绿」和「没跑」长得一模一样。
>
> 现在：最便宜的一段（`precommit.py`）接成本机 `.git/hooks/pre-commit`；
> 两个亚秒级静态闸门接进 `precommit.py --all` 与 `verify_all.py` 第 0 步。
> E2E 与证伪**故意不**进钩子 —— 它们要开浏览器、分钟级，
> 塞进每次提交会变成没人愿意等的门。
>
> ⚠️ `.git/` 不进版本库，所以**每台机器要装一次**：
> `exec python "$(git rev-parse --show-toplevel)/tools/precommit.py"` 写成 `.git/hooks/pre-commit`。

### `verify_all.py` 的 5 步（按成本从低到高）

1. 面板 DOM 契约闸门（亚秒静态）
2. 单元（2 秒）
3. 证伪（分钟级，**会改源码**）
4. E2E（分钟级）
5. 压缩包真加载

> 面板契约排在**最前**是刻意的：它亚秒级，而 E2E 与证伪是分钟级 ——
> 排在后面等于让人等两分钟才发现「面板上那个 id 拼错了」这种一秒能看出的事。

## 3. E2E 闸门（9 条）

| 闸门 | 判据 |
|---|---|
| 扩展能加载 | SW 注册 + 主面板可打开 + 统计卡渲染出数字（**第一天先单独验这条**） |
| dry-run 零写入 | 预览后书签树逐字节不变，且**必须先确认预览算出了待移动条目** |
| 幂等 | 执行后重新预览 → 0 变更、全部在位 |
| 回滚 | 执行整理后恢复到快照，书签树回到执行前 |
| 去重不误删 | 同 URL 判为重复，SPA 不同路由**不**判为重复 |
| 断点续跑 | 中途硬关浏览器 → 重开 → 点继续 → 结果与不中断一致 |
| SW 回收后数据可读 | 硬刷新后仍能读出完整计划（防「计数有值但列表空」） |
| 锁定 | 锁定的条目不进执行队列 |
| 去重逐条否决 | 勾了「不删」的条目执行后**仍在**，没勾的**照删** |
| 手动范围：两组对照 | 勾的 2 条被移动，没勾的 4 条 `parentId` 一条都不变 |
| 手动范围：不删除 | 夹具里那对真重复项执行后一条不少，书签总数不变 |
| 手动范围：范围写进弹窗 | 确认弹窗写明「清单外 N 条一条都不会移动」与归入位置，删除条数是 0 |
| 手动范围：失效不认领 | 勾完删掉其中一条（同 URL 留一条替身）→ 标「已失效」，**替身原地不动** |

> 手动范围的判据**必须两组对照**：只断言「没勾的没动」的话，
> 一个把执行循环整个短路的实现也能变绿 —— 而「该勾的动了」才是那个对照组的作用。
> 见 `tests/e2e/scope-run.js`。
>
> 「失效不认领」那条尤其关键：夹具里那条被删的书签**故意留了一条同 URL 的替身**。
> 若对账按 URL 认领，替身会被整理，而替身是用户没勾的 ——
> 那正是决策 13 要挡的事，而且症状是「整理成功」而不是任何报错。

> 「去重逐条否决」用**两组**重复项做对照。只造一组的话，把唯一那条待删项勾掉后执行器一条都不删，
> 「无论勾什么都全跳过」的实现也能让它变绿 —— 那种闸门测不出东西。
> 它的判据是端到端的**用户可见承诺**；执行器「不信任上游过滤」那道独立复查
> 由 `tests/unit/veto.test.js` 覆盖（E2E 走真实用户路径，构造陈旧 payload 属于绕过前端）。
>
> ⚠️ 那条用例的断言**只能按组断言**，不能断言具体哪一条被删。
> 「保留项」不是夹具决定的，是 Chrome 分配的 id 决定的：两条候选路径深度相同、
> 又是同一毫秒创建，`dateAdded` 完全相同，于是 `compareKeeper` 落到 id 升序，
> 而带不带跟踪参数谁拿到小 id 是不确定的（实测两种都出现过）。
> 早先断言「带 `?spm=abc` 的那条必须消失」，于是这条闸门**随机红绿**。
> 现在断言的是真正的不变量：A 组（勾了不删）两条都在，B 组（没勾）只剩一条。

### 跑 E2E

默认 **headless**，不会弹窗。需要肉眼看着它跑的时候：

```bash
BO_E2E_HEADED=1 npm run test:e2e      # 开窗（调试用）
BO_E2E_CHANNEL=chrome npm run test:e2e # 强制换浏览器通道
BO_E2E_EXT_PATH=D:/no-space/ext npm run test:e2e  # 扩展已在无空格路径时跳过复制
```

| 命令 | 覆盖 |
|---|---|
| `npm run test:e2e` | 主干 9 条（加载 / 零写入 / 幂等 / 回滚 / 去重 / 断点续跑 / 回收后数据可读 / 锁定 / 逐条否决） |
| `npm run test:scope` | 手动范围 3 条（两组对照 / 确认弹窗文案 / 失效不按 URL 认领） |

> ⚠️ **单跑一条用例会红，不代表代码有问题。** 本机实测「去重逐条否决」
> 隔离跑与跟着全套跑结果不同 —— 断言对象押在了 id 分配上（详见上一段）。
> 判断回归时**要么跑全套，要么先在原始 HEAD 上跑同一条做对照**，
> 别拿「单独跑红了」直接当回归证据。

### E2E 的硬约束，全部来自本机已实证的坑

- **`chromium_headless_shell` 不支持加载扩展**，而 Playwright 自带的 chromium 在
  `headless: true` 时用的正是它。
  **但走 `channel`（系统 Chrome/Edge）时，`headless: true` 用的是真实浏览器的新
  headless 模式，扩展照常工作**（本机 Edge 154 实测 service worker 正常出现）。
  → 本 harness 走 channel，**默认 headless**，跑测试不再弹窗。
    要肉眼调试用 `BO_E2E_HEADED=1`。
- **Chrome 155 已移除 `--load-extension`**（本机实测：换无空格路径、
  加 `--disable-features=DisableLoadExtensionCommandLineSwitch` 与
  `--enable-unsafe-extension-debugging` 全部无效）；**Edge 154 仍支持**。
  通道链 `msedge → chrome → chromium` **只对「二进制缺失」这一类错回退**，
  其他错误立刻抛 —— 把真问题降级成「换个浏览器再试试」会把排查带偏一整轮。
- **扩展路径不能含空格。** `--load-extension=F:\test\Label Management\…`
  会被 Chrome 解析失败，症状是**浏览器正常启动、扩展根本没加载**，
  只表现为 `waitForEvent('serviceworker')` 超时。极易误判成「扩展坏了」。
- **复制扩展时路径必须在进程内稳定。** unpacked 扩展的 id 由**绝对路径哈希**而来，
  路径一变 id 就变，而 `chrome.storage.local` 按扩展 id 分区。
  于是「跑一半关浏览器、同 profile 重开继续跑」这类用例会读到**空的
  `task:current`**，症状是「执行记录整个消失了」——
  而真实原因是一个没人会想到的临时目录名。`resolveExtPath()` 已按进程 memo。
  这条专坑「多次 launch + 依赖 storage 续跑」的用例，比如断点续跑。
- 必须 `launch_persistent_context` + **每次全新 `user_data_dir`**。
  复用同一 context 改扩展产物，Chrome 会命中资源缓存 —— 看着像「闸门无效」，
  其实是坏实现从未运行过。
- 断言走**真实用户路径**（点按钮、读表格 DOM），不直接调应用内部函数。
  只有「造夹具」和「读书签树」用 `chrome.*` API。
- 夹具用 `chrome.bookmarks.create()` 在测试内造，**不改磁盘 `Bookmarks` 文件** ——
  固定种子，避免夹具漂移导致「E2E 红了分不清是代码缺陷还是夹具问题」。
- 等待判据必须是**单调递增的量**（`previewSeq`）或**精确的单元格值**（`#reportStatus`），
  不能用「某文本出现了」这类本来就可能成立的子串匹配。

### ⚠️ 覆盖缺口（2026-10-06 实测）

`tests/e2e/*.js` 对**链接健康 / 内容归档 / 语义去重三块面板零覆盖**（grep 过）。
尤其**归档链的最后一跳从未实跑过**：起接收器 → 面板点归档 → 磁盘上真的多出 `.html`，
被星标的还多出 `.pdf`/`.png`。这条链的每一跳都各自有单测，
而**跳与跳之间的接缝没有任何自动化守着**。

补法见 `.scratch/link-scan/issues/`（spec §8 要求的 E2E 工单，尚未开）。

## 4. 手术刀：追具体症状的脚本

这些脚本大多是为追「预览里分类看着是对的，点「执行整理」后书签页却毫无动静」
这一个症状写的。全部用全新 profile 起真实浏览器。

| 命令 | 回答什么问题 |
|---|---|
| `npm run test:repro` | 复刻完整用户流程：预览 → 手动改判（✗改）→ 执行 → 逐条核对落位 |
| `npm run test:real` | **用户真实数据**复刻：真实 URL、真实目录结构、LLM 开着。另钉一条披露闸门——面板必须自己说清结果落在哪个根 |
| `npm run test:matrix` | 9 种真实场景：书签在旧文件夹里、归入位置改成「其他书签」、已有同名文件夹、150 条批量、源目录 4 层深、类目名带斜杠、连续点两次执行…… |
| `npm run test:llm` | LLM 兜底三条路径：正常返回 / 网络报错 / **请求挂住**。最后一条验的是「挂住时能不能自愈」 |
| `npm run test:revert` | 把 `move()` 换成「搬完就改回」，模拟另一个扩展 / 同步覆盖。断言执行器**必须报失败**而不是报成功，且失败原因可操作 |
| `npm run test:stale` | 把书签**删掉再按同 URL 重建**（id 全变，书签还在）→ 断言执行器能按 URL 自愈并搬成功；再全删干净 → 断言**拒绝启动**而不是跑出 45 条同样的失败 |
| `node tests/e2e/probe-errid.js` | 探针：Chrome 到底对哪些故障报哪句话（判断错误文案能不能直接透传） |
| `npm run test:scale` | 800 条的真实规模：能不能跑完、每条多久、跑完是否全部落位 |
| `npm run test:fail-log` | 失败日志链路：接收器开着时**磁盘文件里必须真出现该条**（判据是读盘，不是接口返回码）；接收器没开时静默降级、一条不丢、「重新导出」可用 |

```bash
npm run test:llm -- ok        # 只跑一个变体
npm run test:real -- --root 2 # 换一个「归入位置」跑
npm run test:scale -- 2000    # 换个规模
```

> `test:llm` 的 `hang` 变体要等满 3 次超时（约 90s）才判定，属正常 ——
> 它的判据是**最终能不能恢复**，不是「多久还没好」。

相关：`docs/lessons-learned.md` 记录了这些脚本本身踩过的坑。
