# 书签整理助手

Chrome MV3 扩展。按「功能」把已收集的书签自动归类到两层中文文件夹，**先预览、确认后再写入**，全程可回滚。

零构建：原生 ES Module，不引打包器。`load unpacked` 直接跑。

---

## 安装

1. 打开 `chrome://extensions`
2. 右上角打开「开发者模式」
3. 点「加载已解压的扩展程序」，选择本目录（含 `manifest.json` 的那一层）
4. 点扩展图标 → 「打开整理面板」

> 另存一份目录拷到别的电脑也能直接加载，扩展不依赖任何本机文件。
> 需要的权限只有 `bookmarks` / `storage` / `unlimitedStorage`。
> **host 权限是按需申请的可选项**，不开 LLM 兜底时一个网站访问权限都不需要。

## 用法

1. **读取并预览** —— 读书签树、存一份备份、算好「哪条从哪搬到哪」。**这一步不动你的任何书签。**
2. 看清单。逐条核对：
   - 点 **✗ 改** 选正确分类 → 当场改判，并**沉淀成规则**，下次更准
   - 点 **✓** → 告诉词典这条判得准，也会固化成规则
   - 勾 **锁** → 这条不会被移动（按 URL 记录，移动过位置也不失效）
3. 去「重复项」页逐条过一遍要删的，**不放心的那条勾「不删」**。
4. **执行整理** → 二次确认弹窗会写明：移动几条、新建几个文件夹、删几条重复项
5. 不满意 → **恢复备份**（Chrome 没有原生撤销，这是唯一退路）

「其他 / 待归类」是给你留的归口。第一轮跑完若有几十条落在这里，
在「设置 → 类目结构」里把它改名或拆开，重跑即可，不用重装扩展。

## 分类是怎么判的

优先级从高到低，首个命中即返回：

| 顺序 | 依据 | 置信度 |
|---|---|---|
| 0 | 面板上手改（`manual:assignments`） | 高 |
| 1 | 人工沉淀的规则（`rules:learned`） | 高 |
| 2 | 域名精确匹配 | 高 |
| 3 | 域名后缀匹配（按点边界） | 中 |
| 4 | 路径关键词 | 中 |
| 5 | 标题关键词 | 低（UI 标黄待确认） |
| 6 | 云端 LLM 兜底（仅对上面都没命中的） | 中 |
| 7 | 落进「其他 / 待归类」 | 低 |

规则表是**纯数据**（`src/classify/dict.js`，37 条规则、804 个域名），不写进任何提示词 ——
确定性、可审计、可单测、零延迟零成本。后缀匹配必须按点边界，
`a.github.com` 命中 `github.com`，但 `notgithub.com` 不会。

## 去重的安全边界

同一页面收藏多次会自动去重，**保留一条、删除其余**。这里最容易出事，所以：

- **保留 hash 路由**。`example.com/#/settings` 与 `example.com/#/profile` 是两个不同页面，
  只有 `#top` / `#_` / `#!` 这类「跳到顶部」的纯锚点才会被剥。
  剥掉 hash 会把不同页面判成重复，进而删掉你真收藏的条目。
- **只剥跟踪参数白名单**（`utm_*` / `from` / `spm` / `share*` 等）。`?id=1` 与 `?id=2` 保留为不同。
- **`http` 与 `https` 视为同一资源**。
- 浏览器内部页（`chrome://`）、本机地址（`localhost`）不参与去重。
- **所有待删条目都会逐条出现在「重复项」清单里，每条都能单独勾「不删」**。
  勾上的条目不进删除清单，确认弹窗会同时显示「已标记为不删」的条数 ——
  勾了却看不到任何变化，就等于没给否决权。
  否决按**条目 id** 记录而不是 URL：同一组的重复项 URL 相同，
  按 URL 记会把保留项也一起保住，去重等于没做。
  执行器在删除前会**再查一次**否决名单，不只信面板的过滤 ——
  面板那一遍可能被上一轮残留的 payload 绕过去，而删除不可逆。

## 备份与回滚

`chrome.bookmarks` **没有导入导出 API**（已核对官方 API 参考页），所以：

- 备份 = `getTree()` 整体序列化 → `chrome.storage.local`（需 `unlimitedStorage`）
- 恢复 = 按快照归位 + 把之后新增的书签移回「其他书签」+ 清掉本次新建的空文件夹 + 重建被删的重复项
- 默认保留最近 10 份，超出按时间淘汰

恢复是**「归位」不是「时间机器」**：它把书签移回快照时的位置，
**不会**撤销你在这期间自己做的编辑。这是能做到的最好程度。

空文件夹的清理由任务记录的 `createdFolders` 精确判定，
不靠「空文件夹」猜 —— 那样分不清是我们建的还是你自己建的。

## 不会自动执行

重排书签树是破坏性操作，扩展**永远不会自动重排**：

- `onCreated` 只累加「待分类 N 条」计数并提示
- 一次 HTML 导入期间会抑制 `onCreated`（官方文档明确要求，
  否则一次导入会触发上千次无效计数）
- 真正整理永远需要你点「执行整理」

## LLM 兜底

规则没命中、落进「待归类」的那一小撮才会发给云端模型 —— **不会外发整个书签列表**。

- 供应商：默认 **DeepSeek**（OpenAI 兼容协议），面板里可切百炼 / OpenAI
- 默认 `baseUrl` = `https://api.deepseek.com`，`model` = `deepseek-flash`，均可改
- **默认开启**（`llmEnabled: true`）。想完全不发数据，去「设置」把它关掉；
  关闭后扩展不需要任何 host 权限
- **API key 只存本机 `chrome.storage.local`**，不进 manifest、不进代码、不进 git
- 权限**按需申请**：点「授权访问该域名」才弹窗；host 权限是
  `optional_host_permissions`，用哪个服务商的才申请哪个

### key 从哪来（两级，优先用面板里手填的）

1. **面板手填** —— 存 `chrome.storage.local`
2. **本机环境变量注入** —— `python tools/inject_key.py` 从环境变量读一次，
   写进 `src/llm-key.local.js`。扩展运行时读不到 OS 环境变量（没有 `process`），
   只能在加载前由本机脚本读一次。
   该文件**已 gitignore、不进发布包**，换台电脑没有它也属正常：
   `llm.js` 用动态 `import()` + `catch` 读它，缺文件会安静退化成「无 key」。

⚠️ key 与区域/服务商**强绑定**：用错端点会 401 或 404。
DeepSeek 官方格式是 `https://api.deepseek.com`（不带 `/v1` 也能通）。
模型名变动较频繁且官方说法互相矛盾（`deepseek-chat` 已公告弃用），
所以给了默认值 + 面板预设列表 + 逐类错误提示，不押注单个名字。
模型被要求**只能用给定类目、不许自造**，返回里不存在的类目会被丢弃。

## 移动失败日志

书签没搬成时，失败原因会记到本机 **`F:\logs\bookmark-organizer\<日期>.jsonl`**，
一行一条（JSON Lines，方便 `grep` 或直接喂 Python）。

### 为什么需要「本机接收器」

**Chrome 扩展没有任意写本地文件的能力。** MV3 没有文件系统 API，
service worker 里连 `showSaveFilePicker` 都不存在（那只在有 DOM 的面板页，
而且必须由用户手势触发）。所以要把日志落到 `F:\logs`，必须由**本机进程**写 ——
这就是 `tools/fail_log_sink.py` 的全部理由。

### 怎么用

```bash
npm run log:sink              # 起接收器（前台）
npm run log:sink:selftest     # 自检：写一条再读回，证明 F 盘真能落盘
```

或直接双击 `tools\start_fail_log_sink.bat`。然后在「设置 → 移动失败日志」里点一次
**「授权本机日志接收器」**（权限按需申请，和 LLM 兜底同一套做法）。

日志在哪儿、什么格式：

```
F:\logs\bookmark-organizer\2026-10-05.jsonl
{"ts":"…","kind":"move","id":"1234","title":"…","url":"https://…",
 "error":"移动后回读：实际在「收集箱」而不是「开发与技术」…",
 "fromPath":["书签栏","收集箱"],"toPath":["开发与技术","前端"],
 "batch":1759679130000,"chrome":"139.0.7258.67","ext":"1.0.0"}
```

- `error` 直接用执行器的 `explainMoveError()` 文案，**已经是可操作的中文**
  （说清实际落在哪、目标在哪、下一步查什么），不用再翻译一遍。
- `batch` 是本轮任务的 `startedAt`：日志按天追加、跨批次混在一起，
  没有它就没法把某一次执行的失败从整月记录里摘出来。
- `kind` 只记失败：`move`（没搬成）与 `delete`（重复项没删掉）。
  **成功条目不记** —— 800 条规模会刷屏，而排查用不上。

### 接收器没开怎么办

**静默降级，不打断整理。** 失败记录会留在扩展的 `chrome.storage.local` 缓冲里
（上限 200 条），在「设置 → 移动失败日志」点 **「重新导出」** 手动存一份。
执行结束时还会再兜底补发一次。

> 「以为记上了、其实没记」是这个项目栽过最多的坑类型，所以面板上永远有一行
> **接收器状态**（在线 / 离线 / 未授权）。那行是判断「到底写没写进去」的唯一依据。

### 端口

`8731`。它只出现在两个地方：扩展侧 `src/fail-log.js` 的 `SINK_PORT`，
接收器侧 `tools/fail_log_sink.py` 的 `DEFAULT_PORT`。**改端口要同时改两侧**，
否则症状是「状态一直显示离线」。

### ⚠️ 两个必须知道的坑

1. **`Access-Control-Allow-Private-Network: true` 不能少。**
   扩展 origin（`chrome-extension://…`）请求 `127.0.0.1` 属于
   「公开来源访问私有网络」（PNA）。少这个响应头，浏览器会**在 service worker 里
   直接把 `fetch` 掐掉**，现象是「失败明明发生了、日志文件一直没生成」——
   和没接一样。`--selftest` 第一步就查这个头。
2. **新模块名不要以写操作模块名结尾。** 零写入闸门是**后缀匹配**
   （`spec.endsWith(bad)`）：把日志缓冲模块叫 `fail-log-storage.js`，
   会被 `storage.js` 命中而报错。日志模块因此只叫 `fail-log.js`。

## 开发

```bash
npm install          # 只装 Playwright（跑 E2E 才需要）
npm test             # 单元测试（Node 内置 test runner，零依赖）
npm run test:falsify # 产品级证伪：改坏真实源码重跑整套，确认闸门会红
npm run test:e2e     # E2E（需要完整 chromium + 有头模式）
node tests/e2e/diagnose.js   # 诊断：打印执行过程中任务状态的推进与失败原因
```

### 「点了执行整理但没变化」的手术刀

这些脚本大多是为追「预览里分类看着是对的，点「执行整理」后书签页却毫无动静」
这一个具体症状写的（判据一律是**用户可见的承诺**）。
它们全部用全新 profile 起真实浏览器，判据一律是**用户可见的承诺**——
每条计划项都得落在它承诺的文件夹里、落在设置指定的根下、再预览必须是 0。
不查 `task.status`（那只是「循环跑完了」，不说明书签动了）。

| 命令 | 回答什么问题 |
|---|---|
| `npm run test:repro` | 复刻完整用户流程：预览 → 手动改判（✗改）→ 执行 → 逐条核对落位 |
| `npm run test:real` | **用户真实数据**复刻（取自 2026-10-05 的现场截图）：真实 URL、真实「文档 / 工作」目录结构、LLM 开着。另钉一条披露闸门——面板必须自己说清结果落在哪个根 |
| `npm run test:matrix` | 9 种真实场景：书签在旧文件夹里、归入位置改成「其他书签」、已有同名文件夹、150 条批量、源目录 4 层深、类目名带斜杠、连续点两次执行…… |
| `npm run test:llm` | LLM 兜底三条路径：正常返回 / 网络报错 / **请求挂住**。最后一条验的是「挂住时能不能自愈」 |
| `npm run test:revert` | 把 `move()` 换成「搬完就改回」，模拟另一个扩展 / 同步覆盖。断言执行器**必须报失败**而不是报成功，且失败原因可操作 |
| `npm run test:stale` | 把书签**删掉再按同 URL 重建**（id 全变，书签还在）→ 断言执行器能按 URL 自愈并搬成功；再全删干净 → 断言**拒绝启动**而不是跑出 45 条同样的失败 |
| `node tests/e2e/probe-errid.js` | 探针：Chrome 到底对哪些故障报哪句话（用来判断错误文案能不能直接透传） |
| `npm run test:scale` | 800 条的真实规模：能不能跑完、每条多久、跑完是否全部落位 |
| `npm run test:fail-log` | 失败日志链路：接收器开着时**磁盘文件里必须真出现该条**（判据是读盘，不是接口返回码）；接收器没开时静默降级、一条不丢、「重新导出」可用 |

```bash
npm run test:llm -- ok        # 只跑一个变体
npm run test:real -- --root 2 # 换一个「归入位置」跑
npm run test:scale -- 2000    # 换个规模
```

> `test:llm` 的 `hang` 变体要等满 3 次超时（约 90s）才判定，属正常 ——
> 它的判据是**最终能不能恢复**，不是「多久还没好」。

### 单元测试

**154 项**，覆盖 URL 归一化、去重、规则匹配、计划生成、类目合并、storage 契约、去重逐条否决、失败日志降级路径。
`tests/fixtures/samples.js` 是命中率闸门的输入（阈值 70%，实测 90.3%）。

`tests/unit/inject-path.test.js` 守的是「`tools/inject_key.py` 写的路径必须是
`llm.js` 真能读到的路径」这条**契约**。它刻意不去测「key 文件在不在」——
那个文件是 gitignore 的、换台电脑就没有，拿它当判据测试会变成随机红。
测契约才既稳定又真的能抓住「路径错一级」这类 bug
（`python tests/falsify_inject_path.py` 会打坏补丁证明这 3 条确实会红）。

`tests/unit/storage.test.js` 给 `chrome.storage.local` 装了个最小替身 ——
storage.js 是全项目最容易**静默**损坏数据的模块，之前只能靠 E2E 间接覆盖，
定位成本极高。有了替身就能在 Node 下直接测两条契约：
① 读-改-写全程持锁（并发 50 次不丢更新）② `mutateMany` 的回调收到的是映射。

`tests/unit/veto.test.js` 同理用替身测「逐条否决」：执行器跳过被否决条目、
否决名单按 id 而非 URL、并发切换不丢更新。它是**双向**钉死的 ——
既钉「该跳过的跳过了」，也钉「没误跳过该删的」。
删掉执行器里那行 `if (isDedupeVetoed(...)) continue`，这 3 条立刻变红。

### 两类闸门，缺一不可

**正向**：`tests/unit/` 断言正确行为。
**证伪**：`tests/unit/falsification.test.js` + `tests/product_falsification.py`
故意造坏实现，确认对应闸门**确实会红**。

`npm run test:falsify` 会备份真实源码、打上坏补丁、跑整套测试、断言变红、再还原。
当前覆盖 9 处退化：剥掉全部 hash、剥掉全部 query、给 `plan.js` 注入写操作 import、
注入**跨行**写操作 import、注入**动态** import 写操作模块、字典位置参数错位、
给 `plan.js` 注入**日志模块**、发送成功后整条清空缓冲、`recordFailure` 不再兜底。

> 绿灯本身不算证据。一道从来没红过的闸门，和没有闸门是一样的。

### E2E 闸门（9 条）

| 闸门 | 判据 |
|---|---|
| 扩展能加载 | SW 注册 + 主面板可打开 + 统计卡渲染出数字（**第一天先单独验这条**） |
| dry-run 零写入 | 预览后书签树逐字节不变，且**必须先确认预览算出了待移动条目** |
| 幂等 | 执行后重新预览 → 0 变更、全部在位 |
| 回滚 | 执行整理后恢复到快照，书签树回到执行前 |
| 去重不误删 | 同 URL 判为重复，SPA 不同路由**不**判为重复 |
| 断点续跑 | 中途硬关浏览器 → 重开 → 点继续 → 结果与不中断一致 |
| SW 回收后数据可读 | 硬刷新后仍能读出完整计划（防「计数有值但列表空」） |
| 锁定 | 锁定的条目不进执行队列 |
| 去重逐条否决 | 勾了「不删」的条目执行后**仍在**，没勾的**照删** |

> 最后一条用**两组**重复项做对照。只造一组的话，把唯一那条待删项勾掉后执行器一条都不删，
> 「无论勾什么都全跳过」的实现也能让它变绿 —— 那种闸门测不出东西。
> 它的判据是端到端的**用户可见承诺**；执行器「不信任上游过滤」那道独立复查
> 由 `tests/unit/veto.test.js` 覆盖（E2E 走真实用户路径，构造陈旧 payload 属于绕过前端）。

E2E 的硬约束，全部来自本机已实证的坑，不是风格偏好：

- **`chromium_headless_shell` 不支持加载扩展**。必须完整 chromium（`channel: 'chromium'`）且**有头模式**。
- 必须 `launch_persistent_context` + **每次全新 `user_data_dir`**。
  复用同一 context 改扩展产物，Chrome 会命中资源缓存 —— 看着像「闸门无效」，
  其实是坏实现从未运行过。
- 断言走**真实用户路径**（点按钮、读表格 DOM），不直接调应用内部函数。
  只有「造夹具」和「读书签树」用 `chrome.*` API。
- 夹具用 `chrome.bookmarks.create()` 在测试内造，**不改磁盘 `Bookmarks` 文件** ——
  固定种子，避免夹具漂移导致「E2E 红了分不清是代码缺陷还是夹具问题」。
- 等待判据必须是**单调递增的量**（`previewSeq`）或**精确的单元格值**（`#reportStatus`），
  不能用「某文本出现了」这类本来就可能成立的子串匹配。

### 三条硬约束在代码里的位置

**`plan.js` 不 import 任何写操作模块。** 这是 dry-run 零写入的全部依据，
由 `tests/unit/plan.test.js` 的静态断言守着（扫源码里的 import）。
import 扫描器覆盖具名/默认/namespace/**副作用导入**/re-export 五种写法 ——
漏掉副作用导入的话，`import './apply.js'` 能整条绕过。

**`storage.js` 的读-改-写在同一个串行临界区内。**
不是「内存累积 + hydrate」——那种写法要防的竞态（并发覆盖、
新 worker 用旧内存态盖掉 storage）恰恰是它自己引入的。
把 `get` 放进临界区后风险整类消失：不存在「内存态」这个可能过期的副本。

**`toPath` 不含根名，`fromPath` 含。** 根归到哪是「写到哪儿」的问题，
由 `settings.targetRoot` 决定，所以 `plan.js` 保持纯函数、不依赖任何设置。
「是否已在位」的比较必须**剥掉 fromPath 的根名**再比，否则两边永远不等，幂等直接失效。
写盘时再把根**名**补回 `toPath`，并由根**名**反查根 **id**（根名随界面语言变，不能硬编码）。

## 实现期间踩到并已修掉的坑

留档，因为它们的症状都极具误导性 —— 大部分表现为「某个功能就是不工作」，
而根因在完全另一个地方。

### 产品代码里的 bug

| 坑 | 症状 | 根因 |
|---|---|---|
| `mutateMany` 回调收到的是 `{key:value}` **映射**，不是单个值 | 落盘对象多出一个嵌套的 `task:current`，`plan` 被重建成 `{items:[]}`，**执行器只搬第一条就停** | `{ ...(cur \|\| {}) }` 把映射整个摊平了 |
| `persistItem` 展开计划项本身 | 状态永远不推进，反复搬同一条，死循环 | 计划项此刻 `status` 还是 `'pending'`，把 extra 里的 `'done'` 覆盖回去了 |
| 路径模型不一致 | 幂等完全失效（每次都重排），且执行一条都搬不动 | `toPath` 不含根名但 `fromPath` 含；`ensureTargetFolder` 拿 `开发与技术` 当根 **id** 去 `getChildren()` |
| `backup.js` 的 `rootIdOf` 返回根**名** | 回滚对根级书签**全部静默失败**（不报错，就是没归位） | `chrome.bookmarks` 只认 id（`'1'`/`'2'`/`'3'`），且根名随界面语言变，不能硬编码 |
| `backup.js` 里 `parentId: '2'` 裸字面量 | 暂时看不出症状，但根 id 解析规则被绕过 | 同文件就有 `rootIdFromName`，硬编码等于把刚修好的规则又破一次 |
| 快照索引的读-改-写跨了锁 | 并发备份时索引互相覆盖，**列表里只剩一条** | `get → 算 → set` 三次独立进出 `serialize()`，中间能被别人插队 |
| 快照 `ts` 从 `new Date().toString()` 抽数字 | 同一秒点两次备份，后一次整个覆盖前一份 | 那是**秒级**精度的本地化字符串，天然会撞；同毫秒内去重要在临界区里做 |
| 去重清单的 `path` 退化成 `['2']` | 恢复出来的重复项**静默落进书签栏** | 把根 **id** 当成根名丢给 `rootIdFromName`，匹配不到就回落到书签栏 —— 不报错 |
| 根名兜底里比对中文字面量 | 英文 Chrome 上根名反查永远失败 | 根标题是**本地化**的，拿「其他书签」四个字去比必然不中，只能按 id 契约回落 |
| `startExecution` 里 `await run()` | 进度条从头到尾空白 | `sendMessage` 的响应要等整批跑完才回来 |
| 中断判定靠时间戳 | 浏览器重开后「继续」按钮永远不出现 | 「5 秒没刷新就算陈旧」不可靠，重开只要 2~4 秒就落在阈值内 → 改用 **SW 探针**（问它「真有循环在跑吗」，消息会唤醒 SW，新实例答 false） |
| **LLM 注入的 key 永远读不到** | 面板一直报「没有 API key」，但用户明明跑过 `inject_key.py`、文件就在磁盘上。**LLM 兜底一次都没跑过**，未分类条目全部落进「其他/待归类」 | `inject_key.py` 写 `src/llm-key.local.js`，而 `src/classify/llm.js` 里写 `import('./llm-key.local.js')` —— 相对 `src/classify/` 解析，指向**不存在的目录**。再叠上 `.catch(() => ({}))` 把加载失败整个吞掉，于是「读不到」和「没注入」报同一句话 |
| `fetch` 没有任何超时 | 网络不通时面板永久停在「LLM 兜底分类中…」：计划表空、**「执行整理」按钮一直禁用**，用户点它等于点空气 | LLM 兜底是 **await 在 `loadAndClassify` 里**的，而它是面板所有交互的入口。一次挂住的连接就冻结整个面板 |
| `loadAndClassify` 的调用点没有 try/catch | 改判后计划表**静默停在旧数据**上、也不报错；用户接着点执行整理 → 书签被搬到**旧分类**里去 | 改判/锁定/否决/恢复都直接 `await loadAndClassify(...)`，读树或 LLM 一抛错，界面就停在不一致的中间态。兜底层坏了不该有能力拖垮主流程 |
| `render()` 不 await 异步渲染 | 执行报告停在旧数字上（任务早已 100% 完成，面板还显示「成功移动 0 / 10」） | `render()` 里的 `renderSnapshots/renderCounts/renderReport` 全是「发射后不管」，而**面板上的数字就是用户判断有没有成功的唯一依据** |
| **面板从不说明「归入位置」** | 「归入位置」是其他书签时，45 条书签全搬到其他书签下的类目文件夹里，原文件夹被搬空但**仍留在书签栏**——书签栏看上去「一点没变」，面板还弹「整理完成」。用户只能靠猜 | 根归到哪由 `settings.targetRoot` 决定，而计划里的 `toPath` **不含根名**（见下面的路径模型）—— 同一份清单在两个设置下产出完全一样，界面上也看不出区别。确认弹窗与完成提示都必须点名根名 |
| 启动被拒时仍提示「已开始执行」 | 点「执行整理」后毫无反应，也没报错 | 后端拒绝启动时返回的是 `{ok:true, result:{started:false, reason}}` —— `ok` 只代表消息送达了。UI 只判 `res.ok`，于是「已在执行中 / 计划为空」都被当成启动成功 |
| 全军覆没时仍提示「整理完成」 | 一条都没搬成，却弹「整理完成」，用户更困惑 | `status=done` 只说明**循环跑完了**，不代表每条都搬成功。失败明细还只藏在「设置 → 执行报告」里，而用户点完执行整理的视线在书签栏和计划表上 |
| **`move()` 后从不回读** | 面板报 100% 成功、失败数 0，书签栏却一点没变，**全程无任何报错** | `chrome.bookmarks.move()` **resolve 只代表请求被受理**。有 `bookmarks` 权限的广告拦截器 / 书签整理类扩展会在书签变更时自动重排（不提示不留痕）、Chrome 同步会覆盖、用户自己会拖动 —— 改动被改回去后执行器一无所知。现每条 move 后立刻 `get()` 回读校验，代价是每条 29.3ms → 36.6ms |
| **计划里的书签 id 全部失效** | 45 条**全部**报 `Error: Can't find bookmark for id.`，而书签都还在树上 | 计划是从一棵**已经不存在的树**算出来的：书签删过又重建、恢复过备份、同步落地过，旧 id 全部失效。早先不校验就硬搬，于是 45 条逐条撞同一句墙。现执行前按 URL 重新定位到活着的节点；一条都对不上则**拒绝启动**并提示重新预览 |
| Chrome 的错误原话直接透传给用户 | 45 条一模一样的英文，用户既不知道是哪条、也不知道该查什么 | 探针实测（`tests/e2e/probe-errid.js`）：Chrome 对**三种不同故障**只有三句话 —— `Can't find bookmark for id.`(源 id 不存在) / `Can't find parent bookmark for id.`(目标文件夹不存在) / `Bookmark id is invalid.`(id 非数字)。不翻译等于零信息量 |
| 复用了用户已有的同名文件夹，却记成「我们建的」 | 回滚时按 `createdFolders` 清理空文件夹，会 `removeTree` **用户自己建的文件夹**（连带里面的书签） | `ensureTargetFolder` 早先无条件把文件夹 id 记进 `createdOut`，不区分「新建」与「复用已有」。改成只在 `ensureFolder` 返回 `created:true` 时记一次 |

### 测试代码里的 bug（更值得记，因为它们让闸门「因为错误的原因」而绿）

| 坑 | 症状 | 根因 |
|---|---|---|
| E2E 只等按钮出现 | 点击丢失，**dry-run 零写入因「什么都没发生」而假绿** | `#btnPreview` 在 HTML 解析时就存在，那时模块还没跑、监听器还没绑 → 加 `body[data-ready]` |
| 等预览结果的条件不唯一 | 随机读到上一轮的旧数据 | 「表格有行**或**空态可见」在 `init()` 之后恒成立 → 改用单调递增的 `previewSeq` |
| `/已完成\|失败\|已暂停/` 匹配报告全文 | 幂等用例在只搬了 4 条时就断言「二次应为 0」 | **报告里永远有一行标签就叫「失败」**，匹配到的是标签不是状态 → 读 `#reportStatus` 单元格的值 |
| 等终态的判据本来就成立 | 续跑用例点「继续」前状态已是终态，等待立即返回 | 「已暂停」本身是终态 → 先显式等「执行中」证明续跑真的启动了 |
| `page.waitForFunction` 传异步谓词 | 报「执行没有产生任何进度」 | Playwright 对 Promise 返回值的真值判断不可靠 → 改成 Node 侧显式轮询 |
| 证伪脚本注入的符号不是真实导出 | 报「这道闸门是摆设」 | 模块直接 SyntaxError，加载失败 ≠ 闸门触发 |
| 证伪脚本过滤掉文件级失败 | 同上 | `not ok N - xxx.test.js` 也是红，早先被判成「没红」 |
| **单测把 bug 固化成了期望** | 报「keySource 应为 none」——而真相是注入的 key 根本读不到 | 断言写死 `keySource === 'none'`，恰好只在 import 路径坏掉时成立。换台机器、bug 修好之后，这条「一直绿的闸门」反而变红。判据必须**由文件系统推导**：文件在就必须读得到 |
| 静态闸门不去注释，匹配到「记录旧坑」的注释 | 报「仍有 `.catch(() => ({}))`」，可实现里根本没有 | 注释里常**故意引用出错的旧写法**来留档。`stripComments` 已从 `tests/helpers/sourceScan.js` 导出，各闸门统一复用，别再各写一份 |
| 判据写成「所有候选路径都必须能解析」 | 为一条**故意留的次选路径**报红 | 次选路径是留给将来挪目录用的，现在解析不到是正常的。强求「全部可解析」只会让闸门变噪声 —— 该钉的是「首个候选能读到」 |

前三条都是同一类错误：**闸门匹配了一个本来就成立的状态**。
一条从没因为真实缺陷红过的闸门，和没有闸门是一样的。

## 已知限制

- **移动设备书签是只读的**，`move()` 进去/出来都会失败，已在扁平化阶段就标出并跳过。
- 分类只吃 **URL + 标题 + 已有文件夹路径**，不抓正文。既是隐私边界，也让几百条书签能秒级完成。
- 只处理**两层**类目（顶层 / 子类）。要更深就在类目名里自己带分隔语义。
- 死链探测**没做**。跨域探测需要 `<all_urls>` 权限，且内网/需登录页面误判率高，
  而「只标记不删」的清单用户还得逐条点开确认，性价比不足。接口位置留着了，日后要做走
  `chrome.permissions.request()` 按需授权。
- 恢复不是时间机器（见上）。
- 不上架 Chrome 商店，自用 unpacked 加载。
